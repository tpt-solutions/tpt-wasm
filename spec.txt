TPT-Wasm — Full Design Specification

Project: tpt-wasm
Language: Rust
Primary license target: MIT
Primary maintainer: TPT project owner
Status: Architecture / greenfield implementation
Primary standards target: WebAssembly Core 3.0, with subsequent versions tracked explicitly
Future standards: WASI, Component Model, relevant WebAssembly proposals

1. Executive Summary

tpt-wasm is an independent Rust implementation of WebAssembly designed around four complementary layers:

┌────────────────────────────────────────────────────────────┐
│                         TPT-WASM                            │
│                                                            │
│  ┌────────────┐  ┌────────────┐  ┌────────────┐            │
│  │   MICRO    │  │    HOST    │  │   FORMAL   │            │
│  │ INTERPRETER│  │ CAPABILITY │  │ VERIFICATION│           │
│  └─────┬──────┘  └─────┬──────┘  └──────┬─────┘            │
│        │               │                │                  │
│        └───────────────┼────────────────┘                  │
│                        ▼                                   │
│                 ┌──────────────┐                           │
│                 │     IR       │                           │
│                 └──────┬───────┘                           │
│                        ▼                                   │
│                 ┌──────────────┐                           │
│                 │    COMPILER  │                           │
│                 └──────────────┘                           │
└────────────────────────────────────────────────────────────┘

The fundamental invariant is:

There is one meaning of a WebAssembly program, expressed formally and embodied by the Micro Interpreter. Every optimized implementation must preserve that meaning.

The project is therefore not principally "a faster WebAssembly runtime."

It is:

A specification-first WebAssembly execution system whose minimal implementation, formal model, host architecture and optimizing compiler are deliberately separated.

2. Project Goals
2.1 Primary goals

tpt-wasm shall provide:

A correct WebAssembly implementation.
A minimal executable reference implementation.
A Rust-native embedding API.
A capability-oriented host architecture.
Explicit resource ownership and isolation.
Deterministic execution modes.
A formal semantic model.
A verification architecture.
An independent compiler IR.
JIT and AOT compilation.
Strong differential testing.
A clean licensing/provenance model.
Integration with the wider TPT ecosystem.
Long-term support for WebAssembly evolution.
3. Non-Goals

tpt-wasm should not initially attempt to:

reproduce Wasmtime's architecture;
reproduce Wasmtime's API;
become a fork of Wasmtime;
make Cranelift the semantic foundation;
implement every WebAssembly proposal immediately;
embed TPT-specific domain semantics into Core Wasm;
make WASI the fundamental host abstraction;
prove the entire optimizing compiler before shipping useful functionality;
become a general distributed-computing framework.

The WebAssembly Component Model itself explicitly takes a layered approach and leaves areas such as persistence, distributed computing and deployment outside its scope. tpt-wasm should retain the same discipline.

4. Standards Strategy

The normative foundation is the WebAssembly specification, not another runtime implementation.

The current Core specification defines:

module structure;
instructions;
validation;
instantiation;
execution;
binary format;
text format;
implementation limits;
formal properties.

The WebAssembly specification repository also provides an official reference implementation and test suite, which should be treated as an interoperability/testing resource rather than as an implementation dependency.

5. Core Architectural Principle

The most important design decision is:

The Micro Interpreter is the Golden Machine.

Everything else is subordinate to the semantic model.

             ┌──────────────────────┐
             │ WebAssembly semantics│
             └──────────┬───────────┘
                        │
             ┌──────────▼───────────┐
             │   Golden Machine     │
             │ Micro Interpreter    │
             └──────────┬───────────┘
                        │
              observable behavior
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
       Compiler        Host         Formal
          │             │             │
          └─────────────┼─────────────┘
                        ▼
                   Verification

This gives the project a stable semantic center.

6. Four-Layer Architecture
Layer 1 — Micro Interpreter

Question:

What does WebAssembly mean?

Characteristics:

small;
obvious;
portable;
deterministic;
easy to inspect;
minimal unsafe;
specification-oriented;
intentionally not optimized.
Layer 2 — Novel Host

Question:

What may a WebAssembly program interact with?

Characteristics:

capabilities;
resources;
explicit authority;
isolation;
deterministic host modes;
TPT integration;
WASI adapters.

WebAssembly itself provides no ambient access to the host; interaction happens through imported/embedder-provided functionality.

tpt-wasm should preserve that principle and make it explicit in its host architecture.

Layer 3 — Formal Verification

Question:

Can we prove that our implementation preserves the specified behavior?

Characteristics:

formal machine;
transition relations;
invariants;
refinement;
memory safety properties;
host capability properties;
eventually compiler correctness.
Layer 4 — Full Compiler

Question:

Can we execute exactly the same semantics efficiently?

Characteristics:

independent TPT IR;
baseline compilation;
optimizing compilation;
JIT;
AOT;
multiple native architectures;
eventually verified transformations.

               │
               ▼
        tpt-wasm-micro

               ▼

     host             TPT adapters

  │
  ▼
IR
  │
  ├── codegen
  ├── JIT

Critical rule

The compiler must not become a dependency of the interpreter.

The host must not become a dependency of the semantic core.

The TPT ecosystem must not become a dependency of Core Wasm.

10. tpt-wasm-format

Represents the WebAssembly module structure.

pub struct Module {
    pub types: Vec<Type>,
    pub imports: Vec<Import>,
    pub functions: Vec<Function>,
    pub tables: Vec<Table>,
    pub memories: Vec<Memory>,
    pub globals: Vec<Global>,
    pub exports: Vec<Export>,
    pub elements: Vec<Element>,
    pub data: Vec<DataSegment>,
}

This is a semantic representation, not an execution representation.

15. Instruction Representation

Initial representation should prioritize clarity:

pub enum Instr {
    Unreachable,
    Nop,

    Block(BlockType),
    Loop(BlockType),
    If(BlockType),

    Br(u32),
    BrIf(u32),
    BrTable(BrTable),

    Return,

    Call(u32),
    CallIndirect(...),

    LocalGet(u32),
    LocalSet(u32),
    LocalTee(u32),

    GlobalGet(u32),
    GlobalSet(u32),

    I32Const(i32),
    I64Const(i64),

    I32Add,
    I32Sub,
    I32Mul,

    // ...
}

Do not optimize this representation.

The compiler gets its own representation later.

16. Execution API

The interpreter should expose an explicit transition:

pub enum Step {
    Continue,
    Return,
    Trap(Trap),
    HostCall(HostCall),
}

and:

pub fn step(machine: &mut Machine) -> Step;

This creates a direct bridge to formal semantics.

17. Traps

Wasm traps must never be represented as Rust panics.

pub enum Trap {
    Unreachable,
    IntegerDivisionByZero,
    IntegerOverflow,
    InvalidConversion,
    MemoryOutOfBounds,
    TableOutOfBounds,
    NullReference,
    IndirectCallTypeMismatch,
    StackOverflow,
    HostFailure(HostError),
}

Implementation errors may panic during development, but a valid Wasm program causing a Wasm trap must always produce a structured Trap.

18. Interpreter Safety Requirements

Target:

safe Rust

for the entire Micro Interpreter wherever practical.

Ideal target:

tpt-wasm-micro
    unsafe blocks: 0

This makes the Micro Interpreter particularly useful as the reference against which optimized implementations are tested.

21. Capability Invocation

Conceptually:

pub trait Capability {
    fn id(&self) -> CapabilityId;

    fn invoke(
        &mut self,
        operation: Operation,
        args: &[Value],
    ) -> Result<Vec<Value>, HostError>;
}

This is intentionally not tied to filesystem, sockets or POSIX.

 │
 │ ResourceId
 ▼

 │

23. TPT-System Integration

tpt-wasm should integrate with tpt-system, but through an adapter:

tpt-wasm
    │
    ▼
tpt-wasm-host
    │
    ▼
tpt-system adapter
    │
    ▼

This prevents the core runtime from becoming dependent on the entire TPT ecosystem.

This is especially important given your plan for tpt-math, engineering, science, FEM, physics, robotics and the other Level-1 TPT systems. tpt-wasm should provide their execution substrate, not absorb their domain models.

25. WASI

WASI should be an adapter layer:

                  tpt-wasm-host
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
        WASI       TPT Host       Custom Host

The WASI interface remains important because WebAssembly's official specification ecosystem defines embedding interfaces separately from the Core specification.

But WASI should not dictate the architecture of the core runtime.

26. Deterministic Execution

Make deterministic execution explicit.

pub enum ExecutionMode {
    Deterministic,
    HostDependent,
    RecordReplay,
}

Deterministic mode:

clock      → virtual
randomness → seeded
filesystem → controlled snapshot
network    → prohibited/recorded
scheduler  → deterministic

This is valuable for:

testing;
reproducibility;
formal verification;
scientific computation;
simulation;
TPT workflows.
27. Layer 3 — Formal Semantics

Crate:

tpt-wasm-semantics

This should define an abstract machine.

Conceptually:

Configuration =
{
    Store,
    FrameStack,
    OperandStack,
    ControlStack

The implementation should mirror the structure of the Core WebAssembly execution semantics rather than inventing a different meaning. The current specification explicitly defines execution semantics and formal properties.

29. Verification Ladder

Do not attempt "fully verified Wasm compiler" immediately.

Use:

V0  Type invariants
 ↓
V1  Interpreter correspondence
 ↓
V2  Memory safety
 ↓
V3  Host capability safety
 ↓
V4  IR refinement
 ↓
V5  Compiler transformation correctness
 ↓
V6  Machine-code refinement

This makes formal verification a continuous architectural property rather than a giant final project.

37. Compiler Correctness

The ideal long-term architecture is:

Core Wasm
    ≈
TPT-Wasm IR
    ≈

    ≈

    ≈

66. Golden Test Principle

For every compiler feature:

program.wasm
    │
    ├── Micro
    │
    ├── Baseline
    │

67. Compiler Optimization Contract

Every optimization must preserve:

values
control flow
traps
memory effects
global effects
table effects
host effects
observable ordering

Not merely return values.

For example, an optimization that changes when a trap occurs may be incorrect even if the eventual return value looks identical.

   ↓

   ↓

   ↓

Then:

and so on.
